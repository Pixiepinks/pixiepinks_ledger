# Customer Question Automation

Administrators open **Quick Messages → Customer Question Automation**. Configure a title and 1–50 flow steps; each question has a stable answer key and up to 1,024 characters of text. Choose **Buttons** for 1–3 options (20 characters each), or **List** for 1–10 options (24 characters each). Lists have a configurable opener button (20 characters), such as “Choose age”; customers tap it to open the options. The starter sequence asks gender, then age band. The first question starts the flow. Each option can lead to a specific question or Finish; “Next question in order” keeps sequential behavior. The server rejects missing destinations, unreachable questions and cycles. Flows use predefined answer routes and staff-selected products; no AI generation is involved.

The separate automation switch defaults to **OFF**. Publishing requires webhook signature verification (`META_APP_SECRET`) to already be configured. No production variable is changed by this feature. Enabling does not enroll existing customers. The conversation owner or administrator explicitly opens **Customer questions → Start questions**; the question-bubble icon is below the message box on desktop; on mobile it is in **More message actions (+)**. Start queues the first real message, so staff should review the configured questions first. Staff with shared read/reply access can view the answers but cannot start/control a sequence they do not own.

Customers select a reply button or list option to receive the next question automatically, even if the staff browser is closed. Arbitrary text does not advance questions. `STOP`, `CANCEL` and `STOP QUESTIONS` stop the sequence; existing marketing withdrawal handling remains responsible for its own STOP semantics. Only signed, exact run/step/token/sender/context/format matches advance a sequence. Button labels are display text; answers come from retained configuration. Receipt, inbound history, answer and next queued step commit together. Question replies bypass AI and marketing consent interpretation. Completing the last question shows preferences in the Inbox panel for staff to use.

Staff can pause, resume or stop. Pausing preserves an already-sent question without resending. Replies while paused or globally OFF remain in chat but do not advance the sequence; after resuming the customer must select the current button again. If a question has expired outside the 24-hour service window, it cannot be sent. Staff may stop it and start a new sequence only after an actual customer reply reopens the window. There are no approved-template or automatic resend fallbacks.

## Runtime and delivery uncertainty

A small worker starts with each web application's ASGI startup and polls durable queued runs every two seconds. Multiple processes serialize through the configuration row and conditional queue claim; no extra Railway service or production setting is required. PostgreSQL holds the configuration/run barrier through each provider request, so an OFF/pause/stop response waits for an already in-flight send, then prevents subsequent sends. SQLite uses `BEGIN IMMEDIATE` for equivalent local serialization. HTTP timeout is 10 seconds. Idle workers never contact Meta.

Before HTTP, `SENDING` is committed. Only a confirmed provider ID permits `WAITING` and an outbound history entry. Missing credentials, timeouts, provider rejection or unparseable acknowledgement become `UNCERTAIN`, never an automatic retry. A process crash after claiming leaves `SENDING`; the panel explicitly treats it as potentially uncertain. Staff must check the chat before stopping/restarting such a run. The application does not claim exactly-once external delivery across a provider/network/process failure.

Each run retains its initial configuration; subsequent admin edits affect new runs. Answers are recorded separately from the older bicycle discovery fields and marketing consent. Per-run lifecycle/answer events and configuration snapshots are retained in an append-only ORM audit table. The staff panel exposes recent event metadata and saved answers; it never exposes actionable button tokens. Sent question buttons appear as non-clickable labels in CRM chat. Automatic question sends are classified as automatic, not staff or AI, in analytics.

Migration `20261108_29` follows `20261107_28`, creates only three new tables and seeds the disabled configuration. No existing conversation, consent, Global AI or audio record is updated. The downgrade retains tables/evidence intentionally; re-upgrade is idempotent. Do not run migrations in production or deploy as part of reviewing this branch.

List support uses optional JSON question fields `type` (`buttons` or `list`) and `list_button`. Existing definitions without `type` continue to use buttons. Existing active runs retain their original snapshot. No new database migration is required. List replies are persisted as `question_list` (within the existing 20-character source column limit), bypass consent/AI processing, and use the same duplicate/uncertainty/window safeguards as button replies.

## Conditional answer routes

The optional `next` array has one entry per option: a question key or `null` to finish. Omitting `next` preserves legacy sequential behavior. Routes live in the existing configuration/run JSON, so no database migration is needed. Runs resolve destinations from their retained snapshot, never from webhook labels or current edited settings. Route decisions are appended to audit history. The builder provides a next-step dropdown for each answer and a flow preview. Renaming or deleting a referenced question leaves a visible missing destination for staff to repair before saving. Different branches can share later questions; all paths must finish and loops are forbidden.

## Flow library

Administrators can keep multiple named flows on the management page. Use **New flow title → Create flow** for a starter, or **Duplicate flow** to copy the selected flow under that title. Select a saved flow to edit and save its questions, option types and routes. Unsaved editor changes prompt before switching flows or using library actions. **Save automation switch** changes only the shared ON/OFF setting and preserves unsaved editor changes.

**Archive flow** hides it from new customer starts and disables editing; **Restore flow** makes it available again. Archiving does not interrupt existing runs. Flows and audit history are retained, with no delete action. The library is limited to 100 saved flows, including archives. Flows may share titles; give them distinct names so staff can choose clearly.

In the Inbox, open **Customer questions → Choose flow**, review the full question/answer route preview, then click **Start questions**. A flow must be explicitly selected. Only active flows appear. Starting passes the selected ID and previewed revision; a changed or archived flow requires a fresh review. Only the conversation owner or administrator can start/control a run. Read-only/shared users retain existing visibility permissions. One unfinished run per customer remains enforced; stop it before starting a different flow.

Migration `20261108_30` follows `20261108_29`. It copies the existing saved definition verbatim into library entry 1, preserves the automation switch/version and every run's retained definition/answers/status, and adds original-flow provenance to historical runs. The PostgreSQL sequence advances after copying ID 1. Re-running or downgrading/re-upgrading retains edited/archived library entries. No customers are enrolled, no messages are sent, and no consent, Global AI or audio settings are modified by the migration. Legacy API requests without a flow ID continue to address the original flow only; the new frontend always submits an explicit selection. The original configuration definition is kept synchronized for legacy flow-1 edits.

## Send selected products

Choose **Send selected products — up to 20** in a step's Answer format. Search the live catalogue (any product range/name/size/SKU), choose a variant, then tick its checkbox. A counter shows 1–20 selected items. Range and price filters apply to the loaded results; load more or search again to discover more. Selected items survive searches and reloads, and can be reordered or removed. Save the flow and route an answer to this product step using its key, for example girls’ age 7 → `girls_age_7_products`. Product steps finish for staff directly, or wait for a product choice first when the follow-up selection option is enabled. Flows support up to 50 steps for separate age/gender selections; configuration requests remain bounded at 256 KiB.

The selected IDs/order and display-only labels are retained in each run snapshot. No products from another range or collection are added automatically. Each exact product/variant is re-resolved against the live Shopify catalogue immediately before sending. Current verified price/title/image/link are used, not cached labels or client-supplied card metadata. Unpublished, unavailable, out-of-stock, unsafe-image or overlong-caption products are skipped and reported. A catalogue outage stops the batch for staff review rather than silently skipping every item. This sends ordinary image+caption cards in the same format as the manual Product button, not a new Meta commerce-catalogue integration.

The worker sends one card per cycle with a durable unique `(run, step, position)` claim committed before external work. Successful cards persist the shared product message metadata and outbound product-reply mapping. Automatic card activity is separated from staff activity in analytics. Every card requires the automation switch ON and an open 24-hour service window. Pause/stop/Global OFF barriers apply between cards; an already in-flight card may finish. Archiving or editing the library flow never changes an active selection. Uncertain or rejected provider outcomes stop all remaining cards and are never automatically retried. After any partial send, staff must inspect the sent count and chat before restarting; use the manual Product button for any specifically reviewed missing card instead of replaying the selection.

Migration `20261108_31` follows `20261108_30` and only adds durable product-send evidence. It does not update existing flow definitions, customers, active runs, Global AI or audio configuration. Evidence survives downgrade/re-upgrade. No migration is executed in production as part of implementing/reviewing this change.

Application rollback note: pause automation before rolling back to a version that predates product steps. Older builders/workers cannot interpret product-step definitions; retaining the evidence table preserves delivery history but does not make an older application understand the new flow format.

### Browse selected products by Shopify collection

In a product step, type a collection name such as “Size 12” into **Search Shopify collections**, click **Find collections**, then choose it in **Shopify collection**. Its currently available products/variants load for ticking. Search within the chosen collection using the product search box. Changing collections clears browse filters but keeps all checked selections and their order. Choose **All products — no collection filter** to return to general search. Saving still stores only your explicitly selected product/variant IDs; it never automatically selects a whole collection or future collection additions.

Collection reads reuse the existing verified discovery limits (up to 200 products, 50 variants per product, a 30-second collection-read budget and shared concurrency slots). Larger or unverifiable collections show a specific error without returning a silently incomplete selection. Unavailable, unpublished, out-of-stock or unsafe-image products remain excluded; select the exact displayed variant/size. No database migration or sending-worker changes are required for collection browsing.


## Numbered cards and a product-choice list

Enable **Ask customer to choose after the cards** in a product step. This mode supports 1–10 selected variants; the existing mode still supports up to 20 cards without a choice list. Edit the **Product-choice message** and **Product-choice button** (for example Sinhala wording with “තෝරන්න”), then save. Previously saved flows/runs are not opted into this mode automatically.

Enabled cards have `1.`, `2.`, etc. at the beginning of their captions; the number is also shown in CRM's product heading, and is not painted onto the photo. The follow-up WhatsApp list contains only confirmed sent cards, with the same numbers. Names are shortened to WhatsApp's 24-character row-title limit. Exact product and variant IDs remain bound to the retained run and per-card send evidence. If a card is skipped, its number is omitted from the list rather than reassigned. If every card is skipped, no empty list is sent.

After the list is accepted, the run waits for the customer's selection. A signed list response must match the sender, run token, step and exact invitation message; only an actually sent product can be selected. The receipt, inbound chat message, exact product answer and completion audit commit together. Duplicate/old/wrong-format replies cannot overwrite the selection. Staff see the chosen card number, full sent product title and variant in the question panel. This records interest, not an order, reservation, payment or marketing consent; staff must confirm current price/availability before taking an order.

The invitation has its own durable send claim (position `-1` in the existing product evidence table), excluded from product counts. Timeouts, lost acknowledgements or crashes do not replay either cards or invitations. Pause/resume and the separate automation switch preserve progress. Migration `20261108_32` adds a nullable 24-character label column, without rewriting definitions or prior records. Downgrade/re-upgrade retains labels and send history. No production migration or deployment is performed as part of implementation.

## Saved Voice and initial greasing service decision

For a bicycle product step, enable the product-choice list, then **After product choice: send Saved Voice, then ask about initial greasing service**. Use **Find Saved Voices** to choose and preview an active, prepared recording. Configure its service charge (LKR) and Sinhala/English question and Yes/No labels. The charge is fixed for every product in that step; use separate age/size product steps when charges differ. The selected recording revision is pinned and its title is shown in the flow preview. Editing/deactivating/re-preparing the recording requires reselecting its current revision; the automation never substitutes or prepares a different recording silently.

After the signed product-list selection is verified, the run saves the selected card's quoted product price, queues the explanation recording, and only then queues the Yes/No question. The question always appends the configured service charge explicitly. Audio must be accepted before the question can be sent. A changed, missing or invalid recording, failed upload or uncertain voice send stops progression for staff review. A known voice-delivery failure before the question is detected. Each stage has its own durable claim; pause/resume preserves sent stages and interrupted/uncertain sends are never automatically replayed. Plain text and product-list answers cannot be treated as a service decision: the customer must tap a bound Yes/No reply button.

Yes records the configured charge and product-price-plus-charge quoted total. No records zero service charge and the product price alone. Product, service decision, voice revision, quoted amounts and audit history remain in the run for staff; the UI shows the decision and quoted total. This does not create an invoice/order, reserve stock, send bank details, request payment or change marketing consent. Staff must verify current price/availability before preparing payment instructions.

The worker uses the unchanged staff Saved Voice audio profile: validated stored OGG/Opus; when the existing FFmpeg flag is enabled, the same normalization function/profile and ordinary-audio flag are used. It writes a separate integrity-checked sent-audio snapshot for private CRM playback without altering the library file or revision. Voice activity is automatic, not staff/AI activity. Starting a flow with this follow-up requires the existing Saved Voices section permission in addition to conversation management permission.

Migration `20261108_33` adds only nullable audio-snapshot evidence to the existing stage-claim table; it does not change Saved Voices tables, audio encoding, configured flows, customer records or Global AI. Existing flows are not opted in. Evidence survives downgrade/re-upgrade. The voice and question use reserved stage positions -2/-3, excluded from product-card counts. As with other new flow formats, pause automation before rolling back to an older application version that does not support this follow-up.


## Delivery details and customer confirmation

In the product step's greasing follow-up, enable **Collect delivery details after service answer**. This is opt-in per step; existing saved flows and running snapshots retain their original behavior. After either Yes or No, Sinhala chat prompts collect **customer name → full delivery address → Phone 1 → optional Phone 2**. This uses ordinary WhatsApp messages and buttons, not a Meta WhatsApp Flow form, so no additional Meta Flow setup is required. The second number can be skipped using the Skip button or by typing `skip`, `none`, `no` or `නැහැ`.

Name (2–100 characters) and address (10–350 characters) must contain letters. Phone numbers are validated and formatted: Sri Lankan local numbers such as `0771234567` become `+94771234567`; international numbers need a country code with `+`. Invalid answers prompt correction. Send one answer per prompt; bursts while the next question is queued do not populate another field. Optional reply contexts must match the current prompt. Non-text messages never populate delivery fields.

After entry, the customer receives a quantity-1 review of the selected product/variant, the original quoted price, chosen greasing charge, **FREE delivery**, total and entered details. **Confirm order** saves a timestamped confirmed order request; **Edit details** re-enters all delivery fields and issues a fresh review. Only the bound confirmation button confirms it; plain text cannot confirm an order. Staff can see the values, collection/review/confirmed status and quote through **Customer questions** in the existing conversation. Details are scoped to that run/conversation and do not overwrite a shared customer profile or an existing sales order.

Confirmation completes this automation for staff invoice preparation. It does not create an invoice/sales order, reserve inventory, send bank details, request payment or mark anything Paid. Staff must check current stock, price and delivery eligibility before invoicing. The quoted free-delivery review is intended for the bicycle flows discussed here; do not enable it for products with delivery charges.

Delivery text uses the signed webhook, same-transaction delivery-ID deduplication, configuration/run locks, durable send claims and existing 24-hour window. Active delivery text is excluded from AI replies and consent interpretation, including while paused/OFF (when it cannot advance). STOP/CANCEL still stops the sequence. Timeouts or crashes never automatically replay a prompt. Sensitive field values are stored in private run answers and normal chat history; audit events reference field names and message IDs rather than duplicating addresses/phone numbers. Each correction/edit creates a new negative claim position starting at -4, excluded from product counts, with a 100-prompt review limit. No additional schema migration is required beyond the existing greasing-follow-up migration `20261108_33`.


## Payment explanation, bank-details image and slip handoff

In a product step with greasing and delivery collection enabled, select **After Confirm order: payment Saved Voice → bank-details image → wait for deposit slip**. Use **Find payment recordings** to select/preview a ready recording explaining how to pay and how to send the slip. Use **Bank-details image** and **Upload bank image** to upload a PNG/JPEG you prepared, review its preview, edit the caption/slip instructions, then **Save settings**. The bank image is required; arbitrary URLs, SVGs and documents cannot be configured as bank images. The existing image-size policy and isolated staff attachment validator apply. Uploading alone never sends anything to a customer.

Both delivery Confirm order and the optional payment configuration are required. Confirmation now queues exactly one payment Saved Voice; only after an accepted voice send does a separate durable claim upload/send the bank image through Meta. The image caption should ask for a clear image/PDF of the deposit slip. Existing flows are not opted in; existing run snapshots do not acquire this feature after a settings edit. Editing/deactivating the selected recording requires reselecting its current ready revision. If either configured asset becomes unavailable, voice delivery is unconfirmed/known failed, or a bank-image send is uncertain, staff must review; no automatic replay occurs. Pause/resume preserves accepted stages and the 24-hour window is checked before sends and after the image upload.

Bank images are immutable content-addressed files under `SAVED_VOICES_DIR/payment-images` on the existing persistent volume. Uploaded bytes are validated before storage. Configuration and retained runs pin a SHA-256 image reference; a later upload cannot replace another customer's retained image. Reads verify the fingerprint. Admin previews are private; sent image playback uses a conversation-scoped attachment route and the retained local image rather than an expiring Meta URL. Payment voice playback uses its private sent-audio snapshot and the same unchanged staff Saved Voice encoding profile. Include this directory in the existing Saved Voices volume backup; no additional database migration or external media host is needed. Unreferenced uploads are retained rather than deleting an image a run might need.

After the bank image is accepted, the run shows **Awaiting deposit slip**. Signed image/PDF attachments received in the same conversation after this stage are linked to the run as **Slip received — awaiting staff verification**. This is a candidate attachment for a human to review, not proof of payment. Plain text such as “I paid”, audio, other document types, stale/wrong-context replies or attachments received while paused/OFF cannot verify payment. Active handoff text/media are excluded from AI processing and consent interpretation. STOP still stops the automation. Receipt metadata, message history and run transition commit atomically, and duplicate webhook IDs do not create another handoff. Staff can open **View submitted payment slip** in the Customer questions dialog; existing Inbox ownership/access rules apply.

The first eligible attachment completes the question automation for human verification. It does not create a SalesPayment, mark an order Paid, reserve stock, generate an invoice or send further messages. Further attachments remain ordinary Inbox messages for staff. Staff must verify the actual bank transfer and use the existing order/payment workflow. Stage positions -200/-201 are reserved for payment voice/bank image and are excluded from product-card counts. Pause/stop payment runs before rolling back to application versions that do not understand these stages.


## Staff bank verification and customer confirmation

After **Slip received — awaiting staff verification**, open **Customer questions → Payment verification** in the customer's Inbox conversation. This requires existing `SALES_ORDERS_ENABLED` and `SALES_PAYMENT_TRACKING_ENABLED` feature settings and the Sales Orders section grant; this change does not enable either setting. Existing order permissions apply: preparing an order requires Create and Transition, while verification requires Record payment claim, Verify payment and Transition. The existing ADMIN-only verification permission is preserved. Conversation owner/administrator access and CSRF protection are also enforced.

Choose **Create order from confirmed details**, or select an existing order matching the same conversation, customer name/address, one selected product/variant, quoted product price, greasing fee, LKR total and free delivery. New-order preparation rechecks current catalogue price and stock; a changed price or unavailable item stops creation for a customer review. Both collected phone numbers remain in the order's contact notes. The primary delivery number is also retained in Alternative phone; the customer's WhatsApp number remains the conversation identity. Preparing the order is idempotent and records customer-confirmation status history. It creates no payment, Shopify order, stock movement or accounting entry.

Check the actual bank transaction, then enter the **actual amount received**, bank transaction date (Sri Lanka date; not in the future) and transaction reference. Tick **I checked this transaction in the bank account**, then **Verify payment & queue confirmation**. This records and verifies one ordinary audited `SalesPayment` using existing transaction-reference deduplication and balance rules. Payment/decision audits, run linkage, order summaries and confirmation queue commit in a single transaction; a failed request cannot leave a half-verified order. Repeating the same request cannot add another payment or replay the message. A different decision for the same slip is rejected.

Full verified payment sets the existing order payment status to **PAID** and moves pre-payment orders to **CONFIRMED** through the existing transition history. A partial amount sets **PARTIALLY_PAID**, leaves the remaining balance and avoids claiming full payment to the customer. Use the existing Sales Order payment workflow for later receipts, and the existing order/fulfilment workflow for Processing, dispatch, tracking and delivery. This action does not post GL entries, reserve inventory, synchronize Shopify or dispatch products.

A separate durable stage (-202) sends a Sinhala payment confirmation with the order reference and amount received; partial-payment wording includes the outstanding balance. The message is attributed to the verifying staff account. The existing Customer Question Automation switch controls the queue independently of Global AI: when OFF, staff can still verify money but the queued message waits. Pausing/stopping the run also pauses/stops notification without reversing the verified bank payment. The 24-hour WhatsApp window still applies. If it closes, payment remains saved; after the customer messages again, **Queue payment confirmation** safely queues an unsent confirmation. Interrupted/uncertain or accepted sends cannot be blindly replayed.

Migration `20261108_34` adds a zero-default `SalesOrder.service_total` without recalculating existing orders or payments. New service amounts are shown separately in the order editor, API and totals. Shopify draft synchronization represents a nonzero service amount as a separate non-shipping, non-taxable custom line and retains the existing remote-total reconciliation checks. Service fees never masquerade as shipping, tax or another bicycle inventory unit. Downgrades retain financial evidence; do not edit service-charged orders with older application versions that do not support the fee.

## Prompt Xpress dispatch and manual Delivered

After the full bank payment is verified, open the linked **Sales Order → Prompt Xpress delivery**. This panel requires the existing Sales Orders, Sales Fulfilment and Sales Delivery Tracking feature settings, Fulfilment operation/Dispatch permissions and access to the linked customer conversation. No settings or grants are enabled automatically.

Once the package is packed, click **Mark packed and ready**. Enter the courier number as `MC` followed by exactly eight ASCII digits, for example `MC12345678`, then click **Dispatch & send tracking** after handing the package to Prompt Xpress. Lowercase `mc` is normalized. The order moves Processing → Dispatched and the shipment moves Ready to dispatch → Dispatched, with audit history and the Sri Lanka dispatch date. The tracking message includes the order reference, number and exactly `https://www.promptxpress.lk/TrackItem.aspx#`; it tells the customer to open the page and enter the number. No undocumented query parameters or automatic courier-status lookup are assumed.

Dispatch and the message claim commit together before the provider call. A repeated dispatch or tracking-message click cannot send another copy. A timeout/crash leaves the message for staff review and never undoes physical dispatch. The WhatsApp 24-hour reply window still applies: when closed, dispatch is saved and no message is sent; once the customer messages again, **Send tracking message** safely sends the unsent details. This is an explicit staff action, independent of the AI and question-automation switches. The message is attributed as a staff text in Inbox analytics.

When staff have confirmed actual delivery, click **Mark Delivered**. Both the local shipment and the sales order become Delivered, the delivery date/timestamp and audit history are recorded, and the action cannot be used before dispatch. No extra customer message, accounting entry, payment change, stock operation or Shopify write occurs. Marking Delivered is manual; visiting the carrier tracking page does not change CRM status. The simple panel handles a single full shipment; partial or multiple shipments retain the existing Fulfilment & Delivery workflow.

The existing tracking editor also validates the `MC` format and canonical link when Prompt Xpress is selected. Other couriers' formats are unchanged. No database migration is needed: existing delivery details, fulfilment history and durable manual-send records are reused.
