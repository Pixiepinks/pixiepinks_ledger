# Customer Question Automation

Administrators open **Quick Messages → Customer Question Automation**. Configure a title and 1–10 ordered questions; each question has a stable answer key and up to 1,024 characters of text. Choose **Buttons** for 1–3 options (20 characters each), or **List** for 1–10 options (24 characters each). Lists have a configurable opener button (20 characters), such as “Choose age”; customers tap it to open the options. The starter sequence asks gender, then age band. The first question starts the flow. Each option can lead to a specific question or Finish; “Next question in order” keeps sequential behavior. The server rejects missing destinations, unreachable questions and cycles. There is no AI generation, conditional branching or product recommendation send.

The separate automation switch defaults to **OFF**. Publishing requires webhook signature verification (`META_APP_SECRET`) to already be configured. No production variable is changed by this feature. Enabling does not enroll existing customers. The conversation owner or administrator explicitly opens **Customer questions → Start questions**; on mobile this is in **Chat options (⋮)**. Start queues the first real message, so staff should review the configured questions first. Staff with shared read/reply access can view the answers but cannot start/control a sequence they do not own.

Customers select a reply button or list option to receive the next question automatically, even if the staff browser is closed. Arbitrary text does not advance questions. `STOP`, `CANCEL` and `STOP QUESTIONS` stop the sequence; existing marketing withdrawal handling remains responsible for its own STOP semantics. Only signed, exact run/step/token/sender/context/format matches advance a sequence. Button labels are display text; answers come from retained configuration. Receipt, inbound history, answer and next queued step commit together. Question replies bypass AI and marketing consent interpretation. Completing the last question shows preferences in the Inbox panel for staff to use.

Staff can pause, resume or stop. Pausing preserves an already-sent question without resending. Replies while paused or globally OFF remain in chat but do not advance the sequence; after resuming the customer must select the current button again. If a question has expired outside the 24-hour service window, it cannot be sent. Staff may stop it and start a new sequence only after an actual customer reply reopens the window. There are no approved-template or automatic resend fallbacks.

## Runtime and delivery uncertainty

A small worker starts with each web application's ASGI startup and polls durable queued runs every two seconds. Multiple processes serialize through the configuration row and conditional queue claim; no extra Railway service or production setting is required. PostgreSQL holds the configuration/run barrier through each provider request, so an OFF/pause/stop response waits for an already in-flight send, then prevents subsequent sends. SQLite uses `BEGIN IMMEDIATE` for equivalent local serialization. HTTP timeout is 10 seconds. Idle workers never contact Meta.

Before HTTP, `SENDING` is committed. Only a confirmed provider ID permits `WAITING` and an outbound history entry. Missing credentials, timeouts, provider rejection or unparseable acknowledgement become `UNCERTAIN`, never an automatic retry. A process crash after claiming leaves `SENDING`; the panel explicitly treats it as potentially uncertain. Staff must check the chat before stopping/restarting such a run. The application does not claim exactly-once external delivery across a provider/network/process failure.

Each run retains its initial configuration; subsequent admin edits affect new runs. Answers are recorded separately from the older bicycle discovery fields and marketing consent. Per-run lifecycle/answer events and configuration snapshots are retained in an append-only ORM audit table. The staff panel exposes recent event metadata and saved answers; it never exposes actionable button tokens. Sent question buttons appear as non-clickable labels in CRM chat. Automatic question sends are classified as automatic, not staff or AI, in analytics.

List support uses optional JSON question fields `type` (`buttons` or `list`) and `list_button`. Existing definitions without `type` continue to use buttons. Existing active runs retain their original snapshot. No new database migration is required. List replies are persisted as `question_list` (within the existing 20-character source column limit), bypass consent/AI processing, and use the same duplicate/uncertainty/window safeguards as button replies.

## Conditional answer routes

The optional `next` array has one entry per option: a question key or `null` to finish. Omitting `next` preserves legacy sequential behavior. Routes live in the existing configuration/run JSON, so no database migration is needed. Runs resolve destinations from their retained snapshot, never from webhook labels or current edited settings. Route decisions are appended to audit history. The builder provides a next-step dropdown for each answer and a flow preview. Renaming or deleting a referenced question leaves a visible missing destination for staff to repair before saving. Different branches can share later questions; all paths must finish and loops are forbidden.

## Flow library

Administrators can keep multiple named flows on the management page. Use **New flow title → Create flow** for a starter, or **Duplicate flow** to copy the selected flow under that title. Select a saved flow to edit and save its questions, option types and routes. Unsaved editor changes prompt before switching flows or using library actions. **Save automation switch** changes only the shared ON/OFF setting and preserves unsaved editor changes.

**Archive flow** hides it from new customer starts and disables editing; **Restore flow** makes it available again. Archiving does not interrupt existing runs. Flows and audit history are retained, with no delete action. The library is limited to 100 saved flows, including archives. Flows may share titles; give them distinct names so staff can choose clearly.

In the Inbox, open **Customer questions → Choose flow**, review the full question/answer route preview, then click **Start questions**. A flow must be explicitly selected. Only active flows appear. Starting passes the selected ID and previewed revision; a changed or archived flow requires a fresh review. Only the conversation owner or administrator can start/control a run. Read-only/shared users retain existing visibility permissions. One unfinished run per customer remains enforced; stop it before starting a different flow.
