# Customer Question Automation

Administrators open **Quick Messages → Customer Question Automation**. Configure a title and 1–50 flow steps; each question has a stable answer key and up to 1,024 characters of text. Choose **Buttons** for 1–3 options (20 characters each), or **List** for 1–10 options (24 characters each). Lists have a configurable opener button (20 characters), such as “Choose age”; customers tap it to open the options. The starter sequence asks gender, then age band. The first question starts the flow. Each option can lead to a specific question or Finish; “Next question in order” keeps sequential behavior. The server rejects missing destinations, unreachable questions and cycles. Flows use predefined answer routes and staff-selected products; no AI generation is involved.

The separate automation switch defaults to **OFF**. Publishing requires webhook signature verification (`META_APP_SECRET`) to already be configured. No production variable is changed by this feature. Enabling does not enroll existing customers. The conversation owner or administrator explicitly opens **Customer questions → Start questions**; the question-bubble icon is below the message box on desktop; on mobile it is in **More message actions (+)**. Start queues the first real message, so staff should review the configured questions first. Staff with shared read/reply access can view the answers but cannot start/control a sequence they do not own.

Customers select a reply button or list option to receive the next question automatically, even if the staff browser is closed. Arbitrary text does not advance questions. `STOP`, `CANCEL` and `STOP QUESTIONS` stop the sequence; existing marketing withdrawal handling remains responsible for its own STOP semantics. Only signed, exact run/step/token/sender/context/format matches advance a sequence. Button labels are display text; answers come from retained configuration. Receipt, inbound history, answer and next queued step commit together. Question replies bypass AI and marketing consent interpretation. Completing the last question shows preferences in the Inbox panel for staff to use.

Staff can pause, resume or stop. Pausing preserves an already-sent question without resending. Replies while paused or globally OFF remain in chat but do not advance the sequence; after resuming the customer must select the current button again. If a question has expired outside the 24-hour service window, it cannot be sent. Staff may stop it and start a new sequence only after an actual customer reply reopens the window. There are no approved-template or automatic resend fallbacks.

## Runtime and delivery uncertainty

A small worker starts with each web application's ASGI startup and polls durable queued runs every two seconds. Multiple processes serialize through the configuration row and conditional queue claim; no extra Railway service or production setting is required. PostgreSQL holds the configuration/run barrier through each provider request, so an OFF/pause/stop response waits for an already in-flight send, then prevents subsequent sends. SQLite uses `BEGIN IMMEDIATE` for equivalent local serialization. HTTP timeout is 10 seconds. Idle workers never contact Meta.

Before HTTP, `SENDING` is committed. Only a confirmed provider ID permits `WAITING` and an outbound history entry. Missing credentials, timeouts, provider rejection or unparseable acknowledgement become `UNCERTAIN`, never an automatic retry. A process crash after claiming leaves `SENDING`; the panel explicitly treats it as potentially uncertain. Staff must check the chat before stopping/restarting such a run. The application does not claim exactly-once external delivery across a provider/network/process failure.

Each run retains its initial configuration; subsequent admin edits affect new runs. Answers are recorded separately from the older bicycle discovery fields and marketing consent. Per-run lifecycle/answer events and configuration snapshots are retained in an append-only ORM audit table. The staff panel exposes recent event metadata and saved answers; it never exposes actionable button tokens. Sent question buttons appear as non-clickable labels in CRM chat. Automatic question sends are classified as automatic, not staff or AI, in analytics.

Migration `20261108_29` follows `20261107_28`, creates only three new tables and seeds the disabled configuration. No existing conversation, consent, Global AI or audio record is updated. The downgrade retains tables/evidence intentionally; re-upgrade is idempotent. Do not run migrations in production or deploy as part of reviewing this branch.

List support uses optional JSON question fields `type` (`buttons` or `list`) and `list_button`. Existing definitions without `type` continue to use buttons. Existing active runs retain their original snapshot. No new database migration is required. List replies are persisted as `question_list` (within the existing 20-character source column limit), bypass consent/AI processing, and use the same duplicate/uncertainty/window safeguards as button replies.

## Conditional answer routes

The optional `next` array has one entry per option: a question key or `null` to finish. Omitting `next` preserves legacy sequential behavior. Routes live in the existing configuration/run JSON, so no database migration is needed. Runs resolve destinations from their retained snapshot, never from webhook labels or current edited settings. Route decisions are appended to audit history. The builder provides a next-step dropdown for each answer and a flow preview. Renaming or deleting a referenced question leaves a visible missing destination for staff to repair before saving. Different branches can share later questions; all paths must finish and loops are forbidden.

## Flow library

Administrators can keep multiple named flows on the management page. Use **New flow title → Create flow** for a starter, or **Duplicate flow** to copy the selected flow under that title. Select a saved flow to edit and save its questions, option types and routes. Unsaved editor changes prompt before switching flows or using library actions. **Save automation switch** changes only the shared ON/OFF setting and preserves unsaved editor changes.

**Archive flow** hides it from new customer starts and disables editing; **Restore flow** makes it available again. Archiving does not interrupt existing runs. Flows and audit history are retained, with no delete action. The library is limited to 100 saved flows, including archives. Flows may share titles; give them distinct names so staff can choose clearly.

In the Inbox, open **Customer questions → Choose flow**, review the full question/answer route preview, then click **Start questions**. A flow must be explicitly selected. Only active flows appear. Starting passes the selected ID and previewed revision; a changed or archived flow requires a fresh review. Only the conversation owner or administrator can start/control a run. Read-only/shared users retain existing visibility permissions. One unfinished run per customer remains enforced; stop it before starting a different flow.

Migration `20261108_30` follows `20261108_29`. It copies the existing saved definition verbatim into library entry 1, preserves the automation switch/version and every run's retained definition/answers/status, and adds original-flow provenance to historical runs. The PostgreSQL sequence advances after copying ID 1. Re-running or downgrading/re-upgrading retains edited/archived library entries. No customers are enrolled, no messages are sent, and no consent, Global AI or audio settings are modified by the migration. Legacy API requests without a flow ID continue to address the original flow only; the new frontend always submits an explicit selection. The original configuration definition is kept synchronized for legacy flow-1 edits.

## Send selected products

Choose **Send selected products — up to 20** in a step's Answer format. Search the live catalogue (any product range/name/size/SKU), choose a variant, then tick its checkbox. A counter shows 1–20 selected items. Range and price filters apply to the loaded results; load more or search again to discover more. Selected items survive searches and reloads, and can be reordered or removed. Save the flow and route an answer to this product step using its key, for example girls’ age 7 → `girls_age_7_products`. Product steps finish for staff directly, or wait for a product choice first when the follow-up selection option is enabled. Flows support up to 50 steps for separate age/gender selections; configuration requests remain bounded at 256 KiB.

The selected IDs/order and display-only labels are retained in each run snapshot. No products from another range or collection are added automatically. Each exact product/variant is re-resolved against the live Shopify catalogue immediately before sending. Current verified price/title/image/link are used, not cached labels or client-supplied card metadata. Unpublished, unavailable, out-of-stock, unsafe-image or overlong-caption products are skipped and reported. A catalogue outage stops the batch for staff review rather than silently skipping every item. This sends ordinary image+caption cards in the same format as the manual Product button, not a new Meta commerce-catalogue integration.

The worker sends one card per cycle with a durable unique `(run, step, position)` claim committed before external work. Successful cards persist the shared product message metadata and outbound product-reply mapping. Automatic card activity is separated from staff activity in analytics. Every card requires the automation switch ON and an open 24-hour service window. Pause/stop/Global OFF barriers apply between cards; an already in-flight card may finish. Archiving or editing the library flow never changes an active selection. Uncertain or rejected provider outcomes stop all remaining cards and are never automatically retried. After any partial send, staff must inspect the sent count and chat before restarting; use the manual Product button for any specifically reviewed missing card instead of replaying the selection.

Migration `20261108_31` follows `20261108_30` and only adds durable product-send evidence. It does not update existing flow definitions, customers, active runs, Global AI or audio configuration. Evidence survives downgrade/re-upgrade. No migration is executed in production as part of implementing/reviewing this change.

Application rollback note: pause automation before rolling back to a version that predates product steps. Older builders/workers cannot interpret product-step definitions; retaining the evidence table preserves delivery history but does not make an older application understand the new flow format.

### Browse selected products by Shopify collection

In a product step, type a collection name such as “Size 12” into **Search Shopify collections**, click **Find collections**, then choose it in **Shopify collection**. Its currently available products/variants load for ticking. Search within the chosen collection using the product search box. Changing collections clears browse filters but keeps all checked selections and their order. Choose **All products — no collection filter** to return to general search. Saving still stores only your explicitly selected product/variant IDs; it never automatically selects a whole collection or future collection additions.

Collection reads reuse the existing verified discovery limits (up to 200 products, 50 variants per product, a 30-second collection-read budget and shared concurrency slots). Larger or unverifiable collections show a specific error without returning a silently incomplete selection. Unavailable, unpublished, out-of-stock or unsafe-image products remain excluded; select the exact displayed variant/size. No database migration or sending-worker changes are required for collection browsing.


## Numbered cards and a product-choice list

Enable **Ask customer to choose after the cards** in a product step. This mode supports 1–10 selected variants; the existing mode still supports up to 20 cards without a choice list. Edit the **Product-choice message** and **Product-choice button** (for example Sinhala wording with “තෝරන්න”), then save. Previously saved flows/runs are not opted into this mode automatically.

Enabled cards have `1.`, `2.`, etc. at the beginning of their captions; the number is also shown in CRM's product heading, and is not painted onto the photo. The follow-up WhatsApp list contains only confirmed sent cards, with the same numbers. Names are shortened to WhatsApp's 24-character row-title limit. Exact product and variant IDs remain bound to the retained run and per-card send evidence. If a card is skipped, its number is omitted from the list rather than reassigned. If every card is skipped, no empty list is sent.

After the list is accepted, the run waits for the customer's selection. A signed list response must match the sender, run token, step and exact invitation message; only an actually sent product can be selected. The receipt, inbound chat message, exact product answer and completion audit commit together. Duplicate/old/wrong-format replies cannot overwrite the selection. Staff see the chosen card number, full sent product title and variant in the question panel. This records interest, not an order, reservation, payment or marketing consent; staff must confirm current price/availability before taking an order.

The invitation has its own durable send claim (position `-1` in the existing product evidence table), excluded from product counts. Timeouts, lost acknowledgements or crashes do not replay either cards or invitations. Pause/resume and the separate automation switch preserve progress. Migration `20261108_32` adds a nullable 24-character label column, without rewriting definitions or prior records. Downgrade/re-upgrade retains labels and send history. No production migration or deployment is performed as part of implementation.
